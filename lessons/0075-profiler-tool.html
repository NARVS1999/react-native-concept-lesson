Phase 9 — Optimization Concepts

Lesson Goal Master the React DevTools Profiler, learn to record profiling sessions, read flame graphs, understand commit phases, identify slow renders, and use why-did-you-render to debug unnecessary re-renders.

React DevTools Profiler

The Profiler is the most important tool for understanding your app's rendering performance. It records every React render and shows exactly how long each component took and why it rendered.

Recording a Profiling Session

// Step 1: Open React DevTools
// Shake your device → "Show Dev Menu" → "Show DevTools"
// Or press Cmd+D (iOS) / Cmd+M (Android) in the simulator

// Step 2: Go to the "Profiler" tab

// Step 3: Click the record button (circle icon) to start recording

// Step 4: Interact with your app — scroll, tap buttons, navigate

// Step 5: Stop recording — the Profiler shows a summary of all commits

// Step 6: Click on individual commits to see the flame graph

// You can also profile specific components using the <Profiler> API:
import { Profiler } from 'react';

const onRenderCallback = (
  id,           // the "id" of the Profiler tree
  phase,        // "mount" (first render) or "update" (re-render)
  actualDuration, // time spent rendering the committed update
  baseDuration,   // estimated time to render entire subtree without memoization
  startTime,      // when React began rendering this update
  commitTime      // when React committed this update
) => {
  console.log(`[${id}] ${phase}: ${actualDuration.toFixed(1)}ms`);
};

function App() {
  return (
    <Profiler id="App" onRender={onRenderCallback}>
      <Header />
      <Profiler id="MainContent" onRender={onRenderCallback}>
        <ContentList />
      </Profiler>
      <Footer />
    </Profiler>
  );
}

Reading Flame Graphs

A flame graph shows the component tree horizontally. Wider bars mean more time spent rendering. The color indicates whether a component updated (blue), re-rendered (yellow), or mounted (green).

// Flame graph anatomy:
//
// ┌─────────────────────────────────────────────┐
// │                App (200ms)                   │  ← top bar = root
// │  ┌──────────┐ ┌──────────────────────────┐  │
// │  │ Header   │ │     MainContent (180ms)  │  │  ← wide bar = slow
// │  │  (20ms)  │ │  ┌────────┐ ┌─────────┐  │  │
// │  └──────────┘  │  │Search  │ │List(150)│  │  │  ← List is the bottleneck
// │                │  │ (10ms) │ │ ██████  │  │  │
// │                │  └────────┘ │Item(15) │  │  │  ← each item takes 15ms
// │                │             │Item(15) │  │  │
// │                │             │Item(15) │  │  │
// │                │             └─────────┘  │  │
// │                └──────────────────────────┘  │
// └─────────────────────────────────────────────┘
//
// Reading tips:
// - Wider = slower (takes more time)
// - Yellow bars = re-renders (not new mounts)
// - Click on a bar to see why that component rendered

// Understanding commit phases:
// "mount" — component rendered for the first time
// "update" — component re-rendered due to state/prop change
//
// What to look for:
// 1. Components that re-render (yellow) when they shouldn't
// 2. Components with unexpectedly wide bars
// 3. Components high in the tree that re-render frequently

Identifying Slow Renders

The Profiler highlights which components are slow. Click on a component in the flame graph to see why it rendered and what changed.

// The Profiler tells you WHY a component rendered:
// "Props changed: a, b" — one or more props changed
// "State changed: count" — setState was called
// "Hooks changed: useMemo" — a hook dependency changed
// "Parent rendered" — the parent re-rendered (most common!)

// Strategy: work from top to bottom
// 1. Find the widest bar in the flame graph
// 2. Check if it should have re-rendered
// 3. If not, add React.memo, useMemo, or useCallback
// 4. Re-record and verify the improvement

// Example: Slow list re-rendering
// Before optimization — every item re-renders when one item changes
function TodoList({ todos, onToggle }) {
  return (
    <FlatList
      data={todos}
      renderItem={({ item }) => (
        <TodoItem todo={item} onToggle={onToggle} /> // all re-render
      )}
    />
  );
}

// After optimization — only changed item re-renders
function TodoList({ todos, onToggle }) {
  const handleToggle = useCallback((id) => onToggle(id), [onToggle]);

  return (
    <FlatList
      data={todos}
      renderItem={({ item }) => (
        <TodoItem todo={item} onToggle={handleToggle} />
      )}
    />
  );
}

const TodoItem = React.memo(function TodoItem({ todo, onToggle }) {
  return (
    <TouchableOpacity onPress={() => onToggle(todo.id)}>
      <Text>{todo.text}</Text>
    </TouchableOpacity>
  );
});

Why-Did-You-Render

The why-did-you-render library patches React to log every unnecessary re-render with details about what changed. It's the fastest way to find re-render causes.

// Install: npm install @welldone-software/why-did-you-render

// Setup in your entry file (index.js)
import React from 'react';
import { AppRegistry } from 'react-native';
import App from './App';

// Enable WDR in development only
if (__DEV__) {
  const whyDidYouRender = require('@welldone-software/why-did-you-render');
  whyDidYouRender(React, {
    trackAllPureComponents: true, // track all pure components
    logOnDifferentValues: true,   // log when props change
  });
}

AppRegistry.registerComponent('MyApp', () => App);

// Add .whyDidYouRender to any component to track it
function ExpensiveComponent({ data, config }) {
  // This component will now log why it re-rendered
  return (
    <View>
      {data.map(item => <Text key={item.id}>{item.name}</Text>)}
    </View>
  );
}
ExpensiveComponent.whyDidYouRender = true;

// Output example:
// [why-did-you-render] ExpensiveComponent re-rendered:
//   Props changed: data (new vs old object reference)
//   This indicates data was recreated on every render.
//   Use useMemo to stabilize the reference.

Practical Profiling Workflow

// Step-by-step profiling workflow:

// 1. Identify the problem area
//    - Use the Performance Monitor (Dev Menu → Show Perf Monitor)
//    - Watch FPS — drops below 30 indicate performance issues
//    - Watch JS Heap — continuous growth indicates memory leaks

// 2. Record a profiling session
//    - Open React DevTools → Profiler tab → Start recording
//    - Perform the slow action 2-3 times for consistent data
//    - Stop recording

// 3. Analyze the flame graph
//    - Find the longest bar — that's your bottleneck
//    - Check if it's mounting (first time) or updating (re-render)
//    - If updating, ask: did the data actually change?

// 4. Apply targeted fixes
//    - Wrap slow children with React.memo
//    - Stabilize function props with useCallback
//    - Stabilize object/array props with useMemo
//    - Move expensive computations out of render

// 5. Verify improvement
//    - Re-record the same action
//    - Compare actualDuration before and after
//    - The bar should be shorter or disappear entirely

// 6. Repeat until all bottlenecks are resolved
//    - Focus on the widest bars first — biggest impact

Mini-Project: Use Profiler to Find Slow Components

Add Profiler instrumentation to your app and optimize the slowest component you find.

import React, { Profiler, useState, useCallback, useMemo } from 'react';
import { View, Text, FlatList, Button, StyleSheet } from 'react-native';

// Profiler callback — logs render times
const onRender = (id, phase, actualDuration) => {
  if (actualDuration > 16) { // longer than one frame (16ms)
    console.warn(`[SLOW] ${id} ${phase}: ${actualDuration.toFixed(1)}ms`);
  } else {
    console.log(`[OK] ${id} ${phase}: ${actualDuration.toFixed(1)}ms`);
  }
};

const ITEM_COUNT = 500;

const Item = React.memo(function Item({ title, index }) {
  return (
    <View style={styles.item}>
      <Text>{index + 1}. {title}</Text>
    </View>
  );
});

export default function ProfilerDemoScreen() {
  const [count, setCount] = useState(0);
  const [filter, setFilter] = useState('');

  const data = useMemo(() => {
    return Array.from({ length: ITEM_COUNT }, (_, i) => ({
      id: String(i),
      title: `Item ${i + 1} — ${Math.random().toString(36).slice(2, 6)}`,
    }));
  }, []);

  const filteredData = useMemo(() => {
    if (!filter) return data;
    return data.filter(item =>
      item.title.toLowerCase().includes(filter.toLowerCase())
    );
  }, [data, filter]);

  const increment = useCallback(() => {
    setCount(prev => prev + 1);
  }, []);

  return (
    <View style={styles.container}>
      <Profiler id="AppRoot" onRender={onRender}>
        <Text style={styles.title}>Profiler Demo</Text>
        <Text>Count: {count}</Text>
        <Button title="Increment (should not re-render list)" onPress={increment} />

        <Profiler id="ItemList" onRender={onRender}>
          <FlatList
            data={filteredData}
            keyExtractor={item => item.id}
            renderItem={({ item, index }) => (
              <Item title={item.title} index={index} />
            )}
            style={styles.list}
          />
        </Profiler>
      </Profiler>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, padding: 16 },
  title: { fontSize: 20, fontWeight: 'bold', marginBottom: 12 },
  list: { marginTop: 16 },
  item: { padding: 12, borderBottomWidth: 1, borderBottomColor: '#eee' },
});

Open the React DevTools Profiler, record while tapping Increment, and verify that the ItemList does NOT appear in the flame graph (since React.memo prevents re-renders). Then intentionally remove React.memo and observe the difference.

Summary

  • The React DevTools Profiler records every render and shows timing information per component
  • Flame graphs show component render time horizontally — wider bars = slower renders
  • Yellow bars = re-renders (updates), green bars = first mounts — focus on unnecessary yellow bars
  • The Profiler tells you WHY a component rendered (props changed, state changed, parent rendered)
  • Work top-down: find the widest bar, check if it should have re-rendered, apply memoization
  • The <Profiler> component lets you instrument specific parts of your component tree
  • why-did-you-render logs every unnecessary re-render with detailed change information
  • Always profile before and after optimization to verify actual improvements

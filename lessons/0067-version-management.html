Lesson 67: Version Management

Phase 8 — Production Concepts

Lesson Goal Understand semantic versioning, platform-specific version codes, and automate version management across your React Native project.

Semantic Versioning (SemVer)

Semantic versioning follows the format MAJOR.MINOR.PATCH and communicates the nature of changes in each release:

VersionFormatWhen to Increment
MAJORx.0.0Breaking changes that require user action
MINOR0.x.0New features that are backward-compatible
PATCH0.0.xBug fixes that don't change functionality

Examples

# Start at version 1.0.0
1.0.0 → Initial release
1.0.1 → Fixed a crash on login
1.1.0 → Added push notifications
1.1.1 → Fixed notification sound on Android
2.0.0 → Redesigned UI (users must re-learn navigation)
2.0.1 → Fixed typo in settings page

Versioning in package.json

{
  "name": "my-react-native-app",
  "version": "1.2.3",
  "scripts": {
    "version:patch": "npm version patch --no-git-tag-version",
    "version:minor": "npm version minor --no-git-tag-version",
    "version:major": "npm version major --no-git-tag-version"
  }
}

Android Version Codes

Android uses two version identifiers:

  • versionName — Displayed to users (e.g., "1.2.3")
  • versionCode — Integer that must increase with each release (used by Play Store)
// android/app/build.gradle
android {
    defaultConfig {
        versionCode 1        // Must increment with each release
        versionName "1.2.3"  // Semantic version string
    }
}

// Example versionCode scheme:
// Major * 10000 + Minor * 100 + Patch
// 1.2.3 → 10203
// 2.0.0 → 20000
// 1.3.1 → 10301

iOS Bundle Versions

iOS uses two version identifiers in the Info.plist:

  • CFBundleShortVersionString — Marketing version shown to users (e.g., "1.2.3")
  • CFBundleVersion — Build number, must increase with each upload to App Store Connect
// ios/MyApp/Info.plist
<key>CFBundleShortVersionString</key>
<string>1.2.3</string>

<key>CFBundleVersion</key>
<string>42</string>

Incrementing iOS build number

# Using agvtool (Xcode command line tool)
cd ios
agvtool new-version -all 43

# Using Fastlane
increment_build_number(
  build_number: 43,
  xcodeproj: "./ios/MyApp.xcodeproj"
)

Automated Version Bumping

Manually updating versions across multiple files is error-prone. Automate it:

Using npm version scripts

# Bump patch version in package.json (without git tag)
npm version patch --no-git-tag-version

# Bump minor version
npm version minor --no-git-tag-version

# Bump major version
npm version major --no-git-tag-version

Custom version bump script

# scripts/bump-version.sh
#!/bin/bash
BUMP_TYPE=$1

# Bump package.json
npm version $BUMP_TYPE --no-git-tag-version

# Get new version
NEW_VERSION=$(node -p "require('./package.json').version")

# Update Android version
cd android
./gradlew -PversionName=$NEW_VERSION updateVersion
cd ..

# Update iOS version (using agvtool)
cd ios
agvtool new-marketing-version $NEW_VERSION
agvtool new-version -all $(($(agvtool what-version | tr -d ' ') + 1))
cd ..

echo "Version bumped to $NEW_VERSION"

EAS Build auto-increment

// eas.json
{
  "build": {
    "production": {
      "autoIncrement": true
    }
  }
}

# EAS Build automatically increments the build number
# for each build on the same platform

Version Management Best Practices

  • Always bump versions before creating a release build
  • Use --no-git-tag-version when you want to manage git tags separately
  • Keep Android versionCode and iOS build number in sync with your release count
  • Consider using tools like standard-version or semantic-release for automated changelogs
  • Tag releases in git with the version number: git tag v1.2.3
  • Test version bumping in CI before relying on it in production

Mini-Project: Set Up Version Management in Your Project

Create scripts to automate version bumping across your React Native project:

# Step 1: Add version scripts to package.json
cat <<EOF > scripts/bump-version.sh
#!/bin/bash
set -e

BUMP_TYPE=\${1:-patch}
if [[ ! "$BUMP_TYPE" =~ ^(patch|minor|major)$ ]]; then
  echo "Usage: ./scripts/bump-version.sh [patch|minor|major]"
  exit 1
fi

echo "Bumping $BUMP_TYPE version..."

# Bump version in package.json
npm version $BUMP_TYPE --no-git-tag-version

# Get the new version
NEW_VERSION=$(node -p "require('./package.json').version")
echo "New version: $NEW_VERSION"

# Update Android
cd android
sed -i "s/versionName \".*\"/versionName \"$NEW_VERSION\"/" app/build.gradle
echo "Android versionName updated to $NEW_VERSION"

# Update iOS
cd ../ios
agvtool new-marketing-version $NEW_VERSION
BUILD_NUM=$(($(agvtool what-version | tr -d ' ') + 1))
agvtool new-version -all $BUILD_NUM
echo "iOS version updated to $NEW_VERSION (build $BUILD_NUM)"

cd ..
echo "Version bump complete!"
EOF

chmod +x scripts/bump-version.sh

# Step 2: Use the script
./scripts/bump-version.sh patch   # 1.0.0 → 1.0.1
./scripts/bump-version.sh minor   # 1.0.1 → 1.1.0
./scripts/bump-version.sh major   # 1.1.0 → 2.0.0

# Step 3: Verify changes
cat package.json | grep version
grep versionName android/app/build.gradle
grep CFBundleShortVersionString ios/MyApp/Info.plist

Run the script and verify all version files are updated consistently.

Summary

  • Semantic versioning (MAJOR.MINOR.PATCH) communicates the nature of changes
  • Android uses versionName for display and versionCode (integer) for Play Store
  • iOS uses CFBundleShortVersionString for marketing and CFBundleVersion for build number
  • Automate version bumping with npm scripts, shell scripts, or EAS auto-increment
  • Always bump versions before creating release builds
  • Keep all version files in sync across package.json, build.gradle, and Info.plist
